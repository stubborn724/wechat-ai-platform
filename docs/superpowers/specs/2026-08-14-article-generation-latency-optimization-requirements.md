# 文章生成延时优化需求文档

## 1. 背景

当前定时文章生成的用户体感时长不稳定。正常单篇内容生成已经能够在数分钟内完成，但多个任务同一时段触发时，后续任务会在全局串行队列中等待；当图片提供商发生响应截断、网络异常或长时间无响应时，单次请求又可能占用 30 分钟超时，并在多级 Provider 降级和任务重试后继续放大。

本需求的目标不是以降低图片质量换取速度，而是在不改变“ERP 产品主体优先、品牌场景受知识库约束、微信草稿不可重复投递”这些业务约束的前提下，消除不必要的等待、重复分析和不可观测的长尾。

### 1.1 已确认的基线数据

| 场景 | 实际执行耗时 | 说明 |
| --- | ---: | --- |
| 无缝海报单篇 | 137-211 秒 | 正常图片 Provider 响应时的常态范围 |
| 普通 ERP 仿写单篇，5 图 | 327 秒 | 绣蔓同类链路的代表值 |
| 3 篇海报，每篇投递 5 个账号 | 897 秒 | 含 15 次微信草稿保存 |
| HTML 多图，13 张 | 1786 秒 | 高图片数任务的正常重任务样本 |
| 异常 ERP 多图 | 2299 秒 | 图片 Provider 长尾与重试放大样本 |

同一时段的 5 个任务已出现以下队列等待：第一个任务等待约 1 秒，最后一个任务等待 1081 秒后才开始执行；最后一个任务自身执行 232 秒，因此用户端总耗时达到 1313 秒，约 22 分钟。

### 1.2 绣蔓图片仿写的现状

绣蔓正式任务 `#11 绣蔓仿写-私域` 和 `#13 绣蔓仿写-公域` 使用固定投喂文章 `#1`，但它们属于 ERP 图生图模式：

- 投喂文章只提供文案结构和表达节奏。
- ERP 产品图是生成图片的唯一视觉主体。
- 知识库提供品牌场景、背景、质感和禁用规则。
- 运行时明确禁止读取、理解或仿写投喂文章原图。

因此，缓存“绣蔓投喂原图的视觉分析 Prompt”不会缩短现有正式绣蔓 ERP 链路，因为该视觉分析本来没有执行。应复用的是已分析的投喂文章版式和稳定视觉约束，而不是复用每张成品图的最终 Prompt。

## 2. 目标与非目标

### 2.1 目标

1. 将正常单篇定时文章的实际执行时间稳定在 2-5 分钟范围内。
2. 将多任务同一时段触发造成的额外排队从 18 分钟级降低到 5-8 分钟以内。
3. 将图片 Provider 异常造成的 20-38 分钟长尾转化为可解释的快速降级或明确失败，目标为 6-10 分钟内收敛。
4. 在固定投喂源场景复用已经持久化的版式、稳定视觉描述和品牌规则，避免重复分析。
5. 保持 ERP 产品主体、图片质量检查、图片归档、公众号草稿投递和重试的幂等性不变。
6. 让运营人员能够在后台区分“排队慢、正文慢、图片 Provider 慢、归档慢、微信投递慢、重试等待”。

### 2.2 非目标

1. 不通过删除图片、降低分辨率或绕过质量检查来制造表面提速。
2. 不将所有图片生成并发数直接提升到 5 或更高，避免 Provider 限流导致整体更慢。
3. 不缓存 ERP 产品相关的完整最终图生图 Prompt。产品、场景、视角和图片位置必须随每篇文章变化。
4. 不允许因并发改造而对同一公众号重复保存草稿或重复直接发布。
5. 不改变现有公域、私域的发布域语义，也不改变已有任务的内容策略。

## 3. 范围与优先级

| 阶段 | 名称 | 优先级 | 解决的问题 |
| --- | --- | --- | --- |
| P0 | 阶段耗时与基线观测 | P0 | 没有数据无法判断优化是否有效 |
| P1 | 图片 Provider 超时、熔断和预算 | P0 | Provider 异常导致的长尾 |
| P2 | 绣蔓固定投喂源复用 | P0 | 固定投喂源的重复结构分析 |
| P3 | 定时任务受控并发 | P1 | 多品牌同一时段全局排队 |
| P4 | 多账号草稿受控并发 | P1 | 5 个账号串行投递 |
| P5 | 非 ERP 投喂原图视觉缓存 | P2 | 纯投喂图片仿写的重复视觉理解 |
| P6 | Agent 结构化输出修复 | P1 | 海报文案 JSON 无效导致的失败 |

P0、P1、P2 必须先于 P3、P4 上线。只有确认 Provider 成功率和平均耗时后，才能安全提高任务并发。

## 4. 需求明细

### 4.1 P0：端到端阶段耗时记录

#### 4.1.1 功能要求

每次 `ScheduledTaskRun` 必须记录下列阶段的开始、结束、耗时和结果摘要：

| 阶段编码 | 阶段名称 | 记录粒度 |
| --- | --- | --- |
| `queue_wait` | 队列等待 | 每个运行记录 |
| `feed_load` | 投喂源和格式模板读取 | 每篇文章 |
| `product_prepare` | ERP 选品、产品名称识别、参考图准备 | 每篇文章 |
| `content_generation` | 标题、正文或海报文案生成 | 每篇文章 |
| `image_prompt` | 图片槽位和动态 Prompt 构建 | 每篇文章 |
| `image_provider` | Provider 请求、降级、归档 | 每张图片、每个 Provider |
| `image_quality_check` | ERP 图片质量检查 | 每张图片 |
| `wechat_delivery` | 保存草稿或发布 | 每篇文章、每个账号 |
| `retry_wait` | 自动重试等待 | 每次重试 |

记录必须包含 `run_id`、`article_id`、`task_id`、Provider 名称、模型名、图片位置、账号 ID、是否命中缓存、是否走降级和脱敏后的失败类别。不得记录 API Key、原始 Base64、完整 Prompt 或微信令牌。

#### 4.1.2 展示要求

后台任务详情至少展示：

1. 总耗时、排队耗时和执行耗时。
2. 每篇文章的阶段耗时瀑布信息。
3. 每张图片使用的 Provider、耗时、是否降级和失败类别。
4. 每个公众号账号的草稿投递耗时与结果。
5. 最近 7 天各任务类型和 Provider 的 p50、p95、失败率和超时率。

#### 4.1.3 验收标准

1. 任意完成、失败或重试中的运行记录均可查询到总耗时和阶段明细。
2. 同一运行的所有阶段耗时之和与实际执行耗时差异不超过 5%。
3. 运营人员无需查看 Worker 日志即可判断慢任务主要阶段。

### 4.2 P1：图片 Provider 分级超时、熔断和文章预算

#### 4.2.1 分级超时

图片 Provider 不得共用 1800 秒全局超时。每个 Provider 必须可单独配置连接、读取和总超时，并由配置名称明确区分。首版建议灰度参数如下，最终值以 P0 数据为准：

| Provider 层级 | 连接超时 | 单请求总超时 | 失败后的动作 |
| --- | ---: | ---: | --- |
| 主 Provider | 10 秒 | 120 秒 | 可降级错误立即切备用 |
| 第二 Provider | 10 秒 | 150 秒 | 可降级错误立即切 Ark |
| Ark Provider | 15 秒 | 180 秒 | 失败后返回聚合错误 |

网络连接异常、响应截断和临时性 5xx 必须立即进入下一 Provider，不能等待到总超时。鉴权、参数、配置错误必须立即失败，不得降级掩盖配置问题。

#### 4.2.2 健康熔断

系统应按 `Provider + 模型 + 操作类型（文生图/图生图）` 维护进程外的健康状态，建议存储在 Redis：

1. 连续 3 次临时失败或超时后，Provider 进入 10 分钟冷却期。
2. 冷却期内的图片请求跳过该 Provider，直接选择下一可用 Provider。
3. 首次半开探测只允许 1 个请求；成功后恢复，失败后重新冷却。
4. 熔断状态必须在后台可见，并可由管理员手动解除。

#### 4.2.3 文章级图片预算

每种任务类型应拥有明确图片阶段预算：

| 任务类型 | 图片数上限 | 默认并发 | 图片阶段预算 |
| --- | ---: | ---: | ---: |
| 无缝海报 | 5 | 3 | 6 分钟 |
| 普通 ERP 图文 | 5 | 2 | 8 分钟 |
| HTML 多图 | 13 | 3 | 15 分钟 |

预算到期后，系统必须停止尚未开始的图片请求，保存每张图片的最终失败原因，并将任务标记为失败或等待人工处理。不得继续在后台无限等待。图片数、并发和预算必须是任务性能档位的一部分，禁止写死在业务流程中。

#### 4.2.4 验收标准

1. 模拟主 Provider 超时后，下一 Provider 在 2 秒内开始请求。
2. 同一 Provider 连续异常时，后续图片不再重复等待其超时。
3. 单篇 ERP 任务在所有 Provider 异常时，图片阶段在 8 分钟预算内结束。
4. 正常 Provider 场景的成功率和图片质量检查通过率不得低于改造前基线。

### 4.3 P2：绣蔓固定投喂源复用

#### 4.3.1 业务规则

绣蔓 `#11`、`#13` 固定使用投喂文章 `#1`。应将该文章已分析的布局模板绑定为任务的显式格式模板版本，并冻结到每一次 `ScheduledTaskRun`。

运行时应直接读取模板中已持久化的内容槽位、图片槽位、标题策略和版式规则，不再重新从原始 HTML 推导布局。投喂文章更新或管理员重新分析时必须创建新的模板版本；已排队、执行中或重试中的运行记录必须继续使用创建时冻结的旧版本。

#### 4.3.2 Prompt 复用边界

允许缓存和复用：

- 投喂文章的 HTML/DOM 结构、槽位顺序、固定标题策略。
- 品牌知识库中稳定的场景、材质、光线、色彩和禁用规则。
- 非 ERP 视觉仿写中，经版本校验后的参考图视觉描述。

必须每次动态生成：

- ERP 产品名称、材质、颜色和主体特征。
- 该篇文章的标题、正文卖点和图片位置。
- 每张图片的空间、视角、构图、使用情境和质量约束。

这样既能省去重复分析，又不会让不同产品套用同一场景 Prompt，造成图片同质化或产品与空间不匹配。

#### 4.3.3 验收标准

1. 绣蔓固定投喂源任务不再执行原始 HTML 布局分析。
2. 同一运行内的模板 ID、版本和内容指纹可在运行记录中追溯。
3. 修改投喂文章后，新运行使用新版本，旧运行不会被污染。
4. 绣蔓 ERP 图生图仍不得调用投喂原图的视觉理解服务。

### 4.4 P3：定时任务受控并发调度

#### 4.4.1 调度规则

现有“全局只能有一个在途运行记录”的逻辑改为“全局受控并发 + 同任务互斥”：

1. 首期允许全局最多 2 个 `ScheduledTaskRun` 同时执行。
2. 同一 `task_id` 同时最多执行 1 个运行记录。
3. 同一运行记录内的多篇文章保持原有顺序，避免 ERP 选品、防重和账号交付语义改变。
4. 同一公众号账号存在直接发布或保存草稿时，必须使用账号级互斥锁，防止外部接口并发冲突。
5. 排队顺序保持按计划日期、计划时间和运行 ID 的稳定顺序；空闲槽位只能领取最早的符合互斥条件的记录。
6. Worker 重启、Celery 重投和 Beat 多实例扫描时，仍必须通过数据库锁和运行 ID 幂等认领，禁止重复生成。

#### 4.4.2 灰度策略

1. 新调度器先以 `max_active_runs=1` 运行，验证行为与旧队列一致。
2. 对测试任务和非高峰时段启用 `max_active_runs=2`。
3. 连续 3 天满足 Provider 错误率、微信失败率和重复发布均不高于基线后，应用到全部定时任务。
4. 出现重复文章、重复草稿、Provider 429 显著上升或数据库锁等待异常时，配置立即回退为 1。

#### 4.4.3 验收标准

1. 五个不同品牌任务同一时段触发时，最多两个运行记录执行，且不出现重复执行。
2. 同一任务的两个时段不会并发生成。
3. 最后一个任务的队列等待 p95 不超过 8 分钟。
4. 任务失败、重试、Worker 重启后，文章和微信交付结果仍保持幂等。

### 4.5 P4：多账号草稿投递受控并发

#### 4.5.1 业务规则

文章生成完成后，多个账号的草稿保存从完全串行改为最大并发 2，后续依据微信接口稳定性可灰度调整到 3。

每个账号投递单元必须：

1. 使用独立数据库会话，禁止并发共享 SQLAlchemy Session。
2. 以 `article_id:account_id` 为幂等键读取和更新 `delivery_results`。
3. 成功后立即持久化结果；后续账号失败时，重试只能补发未成功账号。
4. 请求已发出但结果不确定时标记为 `ambiguous`，禁止自动重投。
5. 同一账号受到 4.4 的账号级互斥锁保护。

#### 4.5.2 验收标准

1. 5 个账号草稿保存的总耗时相对串行基线降低至少 35%。
2. 模拟第三个账号失败后重试，前两个成功账号不会再次调用微信接口。
3. 任意账号出现不确定结果时，系统不会自动创建重复草稿。

### 4.6 P5：非 ERP 投喂原图视觉分析缓存

本项只适用于“投喂文章原图是图片仿写视觉来源”的非 ERP 路径，不适用于绣蔓正式 ERP 任务。

#### 4.6.1 缓存键和失效

视觉分析缓存必须持久化在数据库，缓存键由以下字段组成：

`feed_article_id + source_content_hash + ordered_image_urls_hash + vision_model + prompt_version`

以下任一变化必须创建新缓存，不得复用旧结果：投喂文章正文、图片 URL 或顺序、视觉模型、视觉理解 Prompt 版本、二维码过滤规则版本。

#### 4.6.2 缓存内容

缓存保存每张可用参考图的稳定视觉描述、原图索引、二维码过滤结果和分析元数据。缓存不保存最终生成图片 URL，也不保存动态产品或文章主题 Prompt。

#### 4.6.3 验收标准

1. 相同投喂文章的第二次生成命中缓存，不调用视觉理解模型。
2. 投喂图片变动后自动失效并重新分析。
3. 二维码图片继续被过滤，且图片槽位顺序不发生错位。

### 4.7 P6：海报文案 Agent 的结构化输出

海报文案 Agent 必须通过模型的 JSON Schema 或等价的强约束输出机制返回结果，不得只依赖提示词要求 JSON。

当返回值不符合 Schema 时：

1. 使用原始响应进行一次短修复请求，最大等待 30 秒。
2. 修复仍失败时，任务标记为 `failed`，保存脱敏后的结构校验错误。
3. 该类错误不得进入图片 Provider 的长时间重试队列。

验收要求：模拟缺字段、非 JSON、数组长度不匹配三类响应时，均能在 30 秒内得到明确失败或修复成功结果。

## 5. 数据与接口要求

### 5.1 新增或扩展的数据对象

| 对象 | 职责 | 关键字段 |
| --- | --- | --- |
| `scheduled_run_stage_metrics` | 保存运行阶段耗时 | run_id、article_id、stage、started_at、finished_at、elapsed_ms、status、metadata |
| `image_provider_health` | 保存 Provider 熔断状态 | provider、model、operation、state、failure_count、open_until、updated_at |
| `reference_visual_analysis_cache` | 保存非 ERP 投喂原图分析 | cache_key、feed_article_id、content_hash、image_urls_hash、analysis_payload、version |
| `ScheduledTaskRun` 扩展字段或关联 | 冻结性能档位与模板 | performance_profile、format_profile_id、template_rotation_version |

所有 JSON 元数据需设置大小上限。数据库迁移必须可重复执行，并为查询运行详情、Provider 统计和缓存命中增加必要索引。

### 5.2 配置要求

以下参数必须来自配置或任务性能档位，禁止散落在业务代码中：

- 每个 Provider 的连接、读取和总超时。
- 熔断连续失败阈值、冷却时间、半开探测数量。
- 各任务类型的图片数上限、图片并发数和图片阶段预算。
- 全局运行槽数、单任务运行槽数、账号投递并发数。
- JSON 修复重试次数和最大等待时间。

生产环境配置变更必须支持不重启或有计划地滚动重启，并保留当前默认值作为回滚配置。

## 6. 测试要求

### 6.1 单元测试

1. Provider 超时、截断、429、鉴权、参数错误的分类与降级路径。
2. 熔断的关闭、打开、半开、恢复和并发请求竞态。
3. 图片预算到期时取消未开始请求，并保留已成功图片的结果。
4. 调度器双槽领取、同任务互斥、账号互斥、Worker 重投和数据库锁竞争。
5. 多账号投递的成功、部分失败、不确定结果与幂等补发。
6. 格式模板版本冻结、绣蔓 ERP 不加载投喂原图视觉分析。
7. 非 ERP 视觉缓存命中、失效、二维码过滤和图片顺序保持。
8. 海报 JSON Schema 修复和不可修复失败。

### 6.2 集成与压测矩阵

必须使用草稿模式，不得向用户直接发布。测试矩阵至少包括：

| 场景 | 验证重点 |
| --- | --- |
| 绣蔓 ERP 5 图单篇 | 产品主体、场景质量、模板复用、执行时长 |
| 无缝海报单篇 | 海报文案 JSON、5 张切片、标题与咨询卡 |
| 3 篇海报 x 5 账号 | 多账号并发、草稿幂等、总耗时 |
| HTML 13 图 | 性能档位、图片预算、Provider 降级 |
| 5 个品牌同一时段 | 两槽调度、排队时间、同任务互斥 |
| 主 Provider 故障 | 快速降级、熔断、失败可解释性 |
| 微信接口超时 | 不确定结果保护和人工核对语义 |

## 7. 上线、监控与回滚

### 7.1 上线顺序

1. 先上线 P0，仅记录指标，不改变调度与超时。
2. 使用草稿任务灰度 P1 和 P2，连续观察至少 3 天。
3. 在非高峰启用 P3 双槽调度，保留单槽回退开关。
4. 最后启用 P4 多账号并发和 P6 结构化输出修复。
5. P5 只在确认存在非 ERP 图片仿写任务时上线。

### 7.2 监控告警

以下情况必须告警：

- 图片 Provider 5 分钟失败率超过 20%。
- 图片 Provider 连续熔断超过 15 分钟。
- 队列等待 p95 超过 8 分钟。
- 单任务执行超过其性能档位预算。
- 同一文章同一账号出现多个成功交付记录。
- `ambiguous` 微信交付结果未在 30 分钟内人工处理。

### 7.3 回滚条件

发现重复草稿、重复发布、ERP 产品主体错误率上升、图片质量检查通过率下降超过 5%、Provider 429 明显增加或数据库锁等待异常时，立即执行：

1. 将调度全局槽数回退为 1。
2. 将账号投递并发回退为 1。
3. 关闭新 Provider 熔断策略，恢复已验证的 Provider 顺序。
4. 保留 P0 指标记录，依据数据修复问题后再灰度。

## 8. 最终验收指标

上线后以连续 7 天生产草稿任务统计为准：

| 指标 | 验收目标 |
| --- | --- |
| 无缝海报单篇执行 p50 | 不超过 3.5 分钟 |
| 普通 ERP 5 图单篇执行 p50 | 不超过 5 分钟 |
| 正常任务执行 p95 | 不超过 8 分钟 |
| 多任务同时触发的队列等待 p95 | 不超过 8 分钟 |
| 5 账号草稿投递总耗时 | 相比串行基线降低至少 35% |
| 图片异常任务收敛时间 | 在所属图片预算内结束 |
| 重复草稿或重复发布 | 0 起 |
| ERP 图片质量检查通过率 | 不低于改造前基线 |

## 9. 实施决策

本需求采用“先消除长尾，再提高并发，最后做缓存”的顺序。绣蔓正式 ERP 仿写不实施投喂原图视觉 Prompt 缓存；其优化重点是固定投喂源格式模板复用、ERP 图片 Provider 的可靠性和受控并发。非 ERP 的图片仿写缓存作为独立能力实现，避免把两条图片链路混在一起并错误影响绣蔓产品图质量。
